## 1. Reality check: GitHub Pages privacy

**Your constraint is correct and important.** Here's the precise situation:

- A **private repo** on GitHub Pro still publishes its Pages site **publicly**. Anyone with the `username.github.io/repo` URL can access every file served by Pages.
- **Private publishing** (restricting who can view the Pages site itself) is only available on **GitHub Enterprise Cloud**, for organization project sites. Not for personal repos, not on Pro, not on Team.
- There is no "unlisted link" mode. The URL is not indexed by Google by default, but it is publicly reachable and guessable.

**Bottom line:** If the repo is private and you enable Pages, the code stays private but the site and all its assets (including any PDFs you serve) become public. "Private repo + Pages" gives a false sense of security.

This matters here because your `papers/` folder contains copyrighted academic articles (Crespin & Ferron 2016, Le Bourhis 2019, Hourcade & Le Bourhis 2024, etc.). Serving these from a public URL is copyright infringement, even if the URL is obscure.

---

## 2. Hosting recommendation (answering #8 first because it constrains everything)

**Recommended approach: split the problem in two.**

| What | Where | Why |
|---|---|---|
| The site (HTML/CSS/JS, JSON data, your own syntheses) | **GitHub Pages** (public) or **Netlify free tier** | Your own work, no copyright issue |
| The PDFs | **Stay in the private repo only**, accessed by cloning | Copyrighted material, not yours to publish |

For the site itself, two realistic options:

**Option A — GitHub Pages, PDFs replaced by links.** The site links each source to its official URL (DOI, Cairn, Légifrance, publisher page). Classmates who want the PDF use their institutional access (ENS/PSL library proxy, Cairn via VPN). This is the cleanest legally. The 8 local PDFs in `papers/` are only available to people who clone the repo.

**Option B — Netlify with site-wide password.** Netlify free tier supports a single password for the whole site (one line in a `_headers` file). You can then serve PDFs directly, because access is restricted. The password is shared with classmates. This is the most practical for "click and read" UX, but it's legally grey (you're still distributing copyrighted PDFs, just behind a weak gate).

**My recommendation: Option A for now.** It's zero-config, stays on GitHub, and avoids copyright risk entirely. If the group later decides the classmates really need direct PDF access, switching to Netlify with password takes 15 minutes.

## 3. Data format: keep markdown, add a structured JSON index

Don't convert the syntheses to JSON. Don't generate HTML manually. Do this instead:

- **`sources.json`** — one structured object per BibTeX key, with metadata fields (see section 4). This is what the site reads at runtime.
- **The synthesis text for each entry lives inside `sources.json`** as a markdown string in a `synthesis` field. No need for 55 separate files — for a corpus this size, a single JSON is simpler and avoids broken links.
- **The `.bib` and the big `.md` remain the source of truth.** A one-time script (Python or Node) parses both and produces `sources.json`. When someone updates the syntheses markdown, they re-run the script.

Why not YAML: JSON is natively consumable by the browser with `fetch()`. YAML would require a parser library. Not worth it for a student project.

Why not split into 55 markdown files: more files to maintain, more build complexity, more things that break. The synthesis text is already keyed by BibTeX key in the big markdown. Extracting it into JSON fields is trivial and keeps the site self-contained.

## 4. Data model: BibTeX key → source card

Each entry in `sources.json`:

```json
{
  "key": "Kingdon1984Agendas",
  "title": "Agendas, Alternatives, and Public Policies",
  "author": "Kingdon, John W.",
  "year": 1984,
  "type": "book",
  "access_status": "FULLTEXT-CIBLE",
  "category": "theorie",
  "themes": ["mise_agenda", "policy_window", "trois_flux"],
  "used_in_chapters": [1, 2],
  "url": "",
  "doi": "",
  "pdf_local": "papers/kingdon-1984.pdf",
  "useful_pages": [
    {"pages": "3-4", "topic": "Définition de l'agenda, distinction governmental/decision agenda"},
    {"pages": "18-20", "topic": "Trois flux, fenêtres, couplage"}
  ],
  "key_quotes": [
    {"page": "3", "text": "the list of subjects to which governmental officials are paying some serious attention"}
  ],
  "synthesis": "Kingdon reste l'un des points d'appui les plus solides..."
}
```

The fields that matter for UX:

- **`category`**: one of `theorie`, `air_interieur`, `institutionnel`. Maps to the three corpus groups defined in the note's section 1.2.
- **`themes`**: freeform tags for filtering. Derive from the note's 4-part structure: `publicisation`, `imputation`, `instruments`, `inegalites`.
- **`used_in_chapters`**: which chapters of the note cite this source. Lets classmates navigate "show me all sources used in Part 3."
- **`useful_pages`**: what makes the "jump to page" feature work.
- **`access_status`**: the legend already in your syntheses (FULLTEXT, FULLTEXT-CIBLE, PARTIAL, INDIRECT).
- **`url`/`doi`**: the official link (DOI resolver, Cairn, Légifrance). This replaces PDF hosting.
- **`pdf_local`**: path relative to repo root. Shown only as "available in repo" if using Option A.

## 5. UX: simplest good experience for students

**Single HTML page. No framework. No build step at runtime.**

### Layout

```
┌─────────────────────────────────────────────────────┐
│  Title: "Air intérieur — corpus et argument"        │
│  Subtitle + authors                                 │
├──────────┬──────────────────────────────────────────┤
│ SIDEBAR  │  MAIN CONTENT                            │
│          │                                          │
│ Argument │  [Filter bar: category | theme | status] │
│ ├ Intro  │  [Search box]                            │
│ ├ Part 1 │                                          │
│ ├ Part 2 │  ┌─────────────────────────────────┐     │
│ ├ Part 3 │  │ 📄 Kingdon (1984)               │     │
│ └ Part 4 │  │ Agendas, Alternatives...        │     │
│          │  │ [FULLTEXT-CIBLE] [théorie]      │     │
│ Toutes   │  │ [▶ Lire la synthèse]            │     │
│ les      │  │ [📎 DOI] [📥 Repo PDF]          │     │
│ sources  │  └─────────────────────────────────┘     │
│          │  ┌─────────────────────────────────┐     │
│          │  │ 📄 Le Bourhis (2019)            │     │
│          │  │ ...                              │     │
└──────────┴──────────────────────────────────────────┘
```

### Interactions

1. **Sidebar navigation by chapter.** Click "Partie 2" → filters source cards to those cited in chapter 2. Click "Toutes les sources" → shows all.
2. **Filter bar.** Dropdowns for category (théorie / air intérieur / institutionnel), theme, access status. These are AND-combined.
3. **Search box.** Client-side filter on title, author, synthesis text.
4. **Source card.** Collapsed by default: author, year, title, badges. Click "Lire la synthèse" → expands to show the full synthesis (rendered from markdown with a tiny library like `marked.js`, ~8 KB).
5. **PDF link.** If `url` or `doi` exists → "Accéder au texte" opens the official page. If `pdf_local` exists → "Disponible dans le dépôt" (or direct link if using Netlify/password option).
6. **Jump to page.** In the expanded synthesis, the "useful_pages" entries appear as clickable chips: `pp. 3-4: Définition de l'agenda`. If you're on Netlify with PDFs, these link to `papers/file.pdf#page=3`. If on GitHub Pages without PDFs, they're informational only.
7. **Download.** If PDFs are served, a download button. Otherwise, just the official URL.

### Tech stack

- **1 HTML file** (`index.html`)
- **1 CSS file** (or inline `<style>`)
- **1 JS file** (~150 lines: fetch JSON, render cards, filter logic)
- **`marked.min.js`** for markdown rendering (~8 KB, loaded from CDN or vendored)
- **`sources.json`** — the data

No React, no Vue, no bundler, no npm. A student who knows basic HTML can read and edit every line.
